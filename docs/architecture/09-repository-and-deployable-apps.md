# 代码仓库与三套可部署应用

状态：proposed
最后校验日期：2026-07-30

## 结论摘要

产品边界已经确认包含手机 Web、云端后端和工作机客户端三块代码。工程组织建议采用一个 Monorepo（单体仓库）管理三套独立应用，而不是现在拆成三个 Git 仓库。

## 推荐结构

```text
ArcMind/
├─ apps/
│  ├─ mobile-web/            # 手机 Web 应用
│  ├─ cloud-server/          # 云端后端服务
│  └─ workstation-client/    # 工作机客户端
├─ packages/
│  ├─ contracts/             # API、事件和错误码 Schema
│  ├─ domain/                # 与语言无关的领域约束和生成输入
│  └─ test-fixtures/         # 跨端契约样例与测试数据
├─ infrastructure/
│  ├─ local/                 # 本地开发依赖编排
│  └─ cloud/                 # VPS 部署、代理、数据与观测配置
├─ docs/
├─ scripts/
└─ .agent-context/
```

目录名称是提议，技术栈确定后可以调整；三套应用和共享契约的职责不能合并。

## 为什么暂不拆三个仓库

| 维度 | 单仓库三应用 | 三个独立仓库 |
|---|---|---|
| 跨端契约变更 | 一次提交可同时更新 Schema、服务端和客户端 | 需要跨仓库版本和发布协调 |
| Codex 上下文 | 一次任务可读取完整端到端事实 | 容易遗漏另一个仓库的影响 |
| 本地联调 | 一套命令可启动所需组件 | 需要分别克隆和对齐版本 |
| 单人维护成本 | 较低 | 较高 |
| 权限隔离 | 目录和 CI 规则即可满足当前阶段 | 仓库级权限更强 |
| 独立发布 | 支持，每个应用单独构建 | 支持 |
| 团队扩张 | 中小团队仍可管理 | 多团队独立自治时更合适 |

当前是单人开发和架构学习项目，跨端契约变化频繁，单仓库收益明显高于三个仓库。

## 独立性要求

即使同处一个仓库，三套应用仍必须：

- 拥有独立入口、依赖声明、构建命令、测试命令和发布产物。
- 不通过相对路径读取另一个应用的内部代码。
- 只通过 `packages/contracts` 生成或校验公开契约。
- 独立配置、版本、健康检查和部署回滚。
- 在 CI（持续集成）中按变更路径运行对应检查，同时保留跨端契约测试。

## 共享代码边界

允许共享：

- OpenAPI（开放接口规范）、JSON Schema（JSON 模式）或事件 Schema。
- 错误码、枚举和契约测试样例的生成输入。
- 与业务实现无关的测试夹具和开发工具配置。

禁止直接共享：

- 云端数据库实体给手机端或工作机端。
- 手机 UI 状态对象给云端领域层。
- 工作机本地执行器实现给云端任务编排器。
- 供应商私有 SDK（软件开发工具包）对象跨应用传播。

如果三端最终采用不同语言，共享目录应保存语言无关 Schema，再为各端生成类型，不能强迫所有应用依赖同一语言包。

## 何时考虑拆仓库

只有出现以下实际需求时再评估：

- 三端由不同团队独立负责且需要仓库级权限隔离。
- 发布节奏完全解耦，单仓库 CI 成为显著瓶颈。
- 工作机客户端需要独立开源或采用不同许可证。
- 云端代码不能向客户端开发人员开放。
- 仓库规模导致工具、克隆和索引成本不可接受。

拆分前必须先建立契约发布机制和兼容窗口，否则只是把目录边界变成协调成本。

## 版本策略

- 产品版本可以有统一里程碑名称。
- `mobile-web`、`cloud-server` 和 `workstation-client` 分别维护可发布版本。
- 公开契约单独版本化，客户端声明兼容范围。
- 同一提交可以同时改变多端，但发布必须按兼容顺序执行。

## 待用户确认

- 是否接受“一个仓库、三套独立应用”作为 V2 的正式代码组织。
- 三套应用目录是否使用上述英文名称。
- 工作机客户端未来是否考虑独立开源。
