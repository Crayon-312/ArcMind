# 三端架构一致性与风险审查

状态：current
最后校验日期：2026-07-30

## 审查结论

手机 Web、云端后端和可选工作机客户端的总体方向成立，职责划分没有根本冲突。当前主要问题不是“缺少第四端”，而是若过早编码，尚未定稿的仓库组织、技术栈、身份方式、HTTPS 和契约 Schema 会造成返工。

## 已确认且合理的部分

- 云端是持续业务中枢，手机与工作机都连接云端。
- 手机 Web 是主要交互入口，不承担长期后台任务。
- 工作机客户端是可选执行扩展，不要求公网 IP。
- 实时语音层不拥有任务和长期记忆事实。
- 工作机通过受控执行器调用 Codex CLI 等工具，而不是重写编程 Agent。
- 三端通过公开契约通信，不直接依赖彼此内部实现。

## 发现的问题与修正

| 编号 | 问题 | 风险 | 修正建议 | 状态 |
|---|---|---|---|---|
| AR-001 | “三个项目”可能被理解为三个 Git 仓库 | 提前增加契约同步和联调成本 | 建议采用单仓库三应用，等待用户确认 | proposed |
| AR-002 | “工作机安装端”只描述安装动作 | 容易遗漏常驻连接、权限、升级和执行器职责 | 统一命名为工作机客户端，安装器作为子组件 | resolved |
| AR-003 | P0 实时语音与“先做文字闭环”看似冲突 | 可能误以为第一批代码必须先接语音 | P0 表示首版产品必需，不表示第一开发顺序 | resolved |
| AR-004 | 完整后端做完再做手机端 | API 与真实交互脱节，返工集中爆发 | 云端基础先行，随后按纵向切片联调 | proposed |
| AR-005 | 云端内部模块过多 | 初期拆微服务造成运维负担 | 首版采用模块化单体，保持逻辑边界 | proposed |
| AR-006 | 公开 API 和事件契约仍为 Markdown 草案 | 无法自动检测跨端兼容 | 编码前转成机器可校验 Schema | open |
| AR-007 | 邮箱注册已确认但登录机制未定 | 身份代码容易重写 | 技术选型阶段先定登录、恢复和撤销 | open |
| AR-008 | HTTPS 可信方案未定 | 手机麦克风、实时连接和推送可能不可用 | 在前端正式开发前完成真机验证 | open |
| AR-009 | 工作机协议和安全边界复杂 | 过早开发会阻塞核心手机体验 | 工作机排在文字、任务和实时语音闭环之后 | resolved |
| AR-010 | 实时语音媒体路径未定 | 浏览器直连与云端代理影响延迟和安全 | 供应商评测时做两种链路原型 | open |
| AR-011 | 三端可能采用不同语言 | 直接共享源码包会形成隐性耦合 | 共享 Schema 并生成各端类型 | proposed |
| AR-012 | 云端成为单点 | 故障影响全部端 | 从首阶段建立健康检查、备份和可恢复任务事实 | open |

## 当前阻塞级问题

开始正式业务代码前至少需要确认：

1. 单仓库三应用是否成为正式决策。
2. 手机 Web、云端后端和主数据库的首阶段技术栈。
3. 邮箱登录与身份恢复方式。
4. 可信 HTTPS 和本地开发证书方案。
5. API Schema、错误模型和数据库迁移工具。

实时语音供应商和工作机技术栈不阻塞第一条文字纵向切片，可以后续定案。

## 不建议的做法

- 一次性搭完所有云端模块后才做第一个页面。
- 先做视觉完整的手机页面，再用模拟数据长期代替真实 API。
- 第一阶段同时开发实时语音、长期记忆、提醒和工作机执行。
- 因为处于单仓库就直接导入另一个应用内部代码。
- 在身份、HTTPS 和数据迁移未明确前上线保存真实对话。
