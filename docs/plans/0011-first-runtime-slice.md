## 目标与边界

### 业务目标

从当前只有文档和机器契约的 `v2` 主线开始，建立 ArcMind Runtime（产品运行时）的三应用物理边界，交付第一个可在永久新 VPS 上真实访问的“邮箱身份 + 文字对话”纵向切片。首轮使用测试邮件与确定性模型适配器验证产品、数据、事件、部署和恢复链路，后续在同一边界内替换为真实 SMTP 与 DeepSeek，不把测试替身伪装成正式 AI 能力。

### 本次包含

- 创建 `apps/mobile-web`、`apps/cloud-server`、`apps/workstation-client`、`packages/contracts` 和 `infrastructure/` 约定目录。
- 实现单一允许邮箱、六位一次性验证码、一次性消费、限速、服务端会话、退出和恢复。
- 实现会话创建、用户文字轮次、确定性模型响应、最终轮次持久化和可重放 SSE 事件。
- 使用 PostgreSQL 18、Alembic、FastAPI、React、Vite、Caddy 和 Docker Compose 建立可测试、可迁移、可回滚的首轮部署。
- 在独立新 VPS 上建立 SSH 密钥、防火墙、Docker、持久卷、可信公网 IP HTTPS 和测试邮件捕获器；只公开 80/443，邮件捕获器只允许 SSH 隧道访问。
- 验证桌面与移动视口的登录、刷新恢复、文字对话、SSE、错误状态、重启恢复和证书链。

### 本次不包含

- 不实现真实模型供应商、真实 SMTP、实时语音、任务中心、记忆、提醒、工作机连接或 Codex 执行。
- 不把工作机客户端部署到 VPS；本次只建立其独立可检查骨架，后续安装在用户个人电脑。
- 不连接或修改旧共享 VPS，不迁移其任何容器、证书、配置或数据。
- 不在生产 VPS 编译前端或构建应用镜像；构建产物必须来自本地或 CI。
- 不把测试邮件与确定性模型结果描述为正式生产能力。

## 证据与判断

### 已确认事实

- 用户确认采用分阶段持续部署，首个闭环选择身份加文字对话，并允许测试适配器先上线。
- `v2` 当前没有被 Git 跟踪的业务实现、依赖清单、数据库迁移、Dockerfile 或运行时发布产物。
- 新 VPS 已只读确认为腾讯云空主机：Ubuntu 24.04.4 LTS、2 vCPU、约 3.6 GiB 内存、60 GB 系统盘和约 1.9 GiB swap，仅 SSH 监听。
- 技术、数据、身份、SSE、HTTPS 和三应用边界已经由正式决策与机器契约确定。

### 合理推断

- 先用确定性适配器完成数据库、身份、SSE、前端和部署闭环，可以把供应商凭据和模型差异从首轮基础设施故障中隔离出来。
- 2 核 4 GB 足以承载首轮单用户静态 Web、单 API 实例、PostgreSQL、测试邮件和低负载后台进程，但必须通过部署后观测确认余量。

### 假设与开放问题

- 腾讯云控制台是否承诺公网 IPv4 固定、是否放行 80/443，以及底层磁盘介质类型仍需外部核对。
- 测试允许邮箱仅作为部署环境值，不进入仓库；上线后由用户通过测试邮件捕获器取得验证码。
- 真机浏览器、一次真实证书续期、异地备份和真实模型/SMTP 仍是后续发布门禁。

## 用户批准的方案

- 2026-08-07，用户明确目标是把新 VPS 作为 ArcMind 后续永久服务器并部署完整项目，而不是只部署 HTTPS 验证页。
- 同日用户确认采用分阶段持续部署，首个发布范围为“身份 + 文字对话”，外部邮件与模型先使用测试适配器。
- 本任务获准在当前 `v2` 工作区创建业务代码、配置服务器、部署首个纵向切片并按既有授权推送；旧共享 VPS 零操作边界不变。
