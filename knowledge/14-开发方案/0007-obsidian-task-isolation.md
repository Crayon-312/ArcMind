## 目标

在不引入服务、数据库、社区插件或每任务强制工作树的前提下，让 `docs/` 可直接作为 Obsidian（本地 Markdown 知识库工具）打开，并建立“讨论隔离—用户批准—清单执行—验证发布”的最小稳定闭环。

## 非目标

- 不修改 ArcMind 产品运行时代码。
- 不安装、启动或控制用户本机的 Obsidian。
- 不创建自动 Canvas（可视化画布）、自定义插件、后台索引服务或发布平台。
- 不为本任务创建新分支或 Git worktree（Git 独立工作树）。
- 不推送远端。

## 已确认依据

- 用户已明确批准实施，并要求直接在当前 V2 分支改造。
- V2 当前是文档和架构建模阶段，没有需要重启的业务运行态。
- Agent Context OS 已提供方案落实台账、执行门禁和按风险选择工作树的通用能力，本仓库只需要项目级落点。
- 当前工作区在任务开始时干净，没有并行任务或共享文件冲突。

## 用户批准的方案

- `docs/` 作为 Obsidian 知识库，Git Markdown 是事实源。
- `docs/plans/` 中每任务一个文件作为隔离任务舱和执行台账。
- 讨论期不改正式事实；用户确认后依照有序清单实施。
- 固定先批准任务舱，代码与正式文档在验证后同步发布；纯文档任务直接按文档验收闭环。
- 工作树按稳定性风险启用，不机械地一任务一个。

## 工作区模式

本任务在现有 `v2` 主工作目录串行执行。用户明确要求不拉新分支；任务开始时工作区干净、没有并行任务、没有业务运行态，额外工作树不能降低已识别风险，因此不创建。

未来同时执行多个任务时，先比较修改文件和运行态是否冲突。只读或互不重叠的小任务可共用工作区并串行提交；会并行改代码、长期占用运行态、风险较高或需要实验隔离的任务使用独立工作树。工作树隔离文件，不会自动解决两个任务修改同一正式文档产生的语义冲突。

## 文档与实现顺序

1. `draft` 任务舱收集证据和备选方案，不改正式文档与代码。
2. 用户批准后，任务舱进入 `confirmed`，完整任务清单成为唯一执行依据。
3. 执行时进入 `active`；目标契约先写在任务舱，随后完成代码、配置、测试和待发布正式文档。
4. 验证真实行为后，正式文档、项目记忆与实现一起形成同一发布闭环，再将任务舱改为 `done`。

本任务是纯文档和配置变更，不存在先改业务代码的问题；Obsidian 结构和协作规则通过结构、链接和项目门禁验收后直接发布。
