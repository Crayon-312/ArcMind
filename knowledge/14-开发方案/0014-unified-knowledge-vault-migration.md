# 方案落实台账：统一知识库结构完整迁移

## 目标与边界

### 业务目标

把 ArcMind 当前 `docs/` Obsidian（本地 Markdown 知识库工具）知识库完整迁移为跨项目统一的 `knowledge/` 结构，使人类能够按稳定知识职责浏览关系网络，使 Agent（智能协作助手）能够从唯一事实源可靠校验、索引、检索和追踪证据。

### 本次包含

- 将知识库根目录从 `docs/` 迁移为 `knowledge/`。
- 使用固定的 `00-15` 软件工程公共领域、`20-79` 项目专属领域和 `90/99/_attachments` 保留区。
- 将现有产品、业务、架构、契约、数据、前端、后端、安全、决策、质量、计划和运行知识按唯一主职责重新归档。
- 将旧 `project-memory/` 中重复复述正式事实的迁移记录转入历史归档，保留追溯但不继续作为并行事实源。
- 建立每个正式领域唯一命名的内容地图，更新全部内部链接和路径引用。
- 更新 Agent Context OS（智能协作上下文操作系统）配置、项目入口、Obsidian 配置和自动门禁。
- 重建本地索引并验证目录、元数据、断链、关系孤岛、内容地图收录和固定检索用例。

### 本次不包含

- 不改变 ArcMind 产品功能、公开接口语义、数据库结构或部署拓扑。
- 不操作生产服务器，不重启生产容器。
- 不修改或提交用户现有未跟踪 `.claude/`。
- 不在项目中复制完整 Agent Context OS 源码。
- 不为不存在的项目能力创建空壳知识目录。

## 证据与判断

### 已确认事实

- 用户明确要求不论改动大小都完整迁移，并要求按统一规范保证人类关系网络与 Agent 数据获取质量。
- 当前知识库共有 138 篇 Markdown（轻量标记文档），唯一知识源为 `docs/`。
- 当前项目存在 `apps/mobile-web`、`apps/cloud-server` 和 `apps/workstation-client` 三个可部署应用，因此前端设计、后端设计、接口与事件、数据模型、运行手册和工作机执行端均为必需领域。
- 当前 91 个文件包含 `docs/` 路径引用，迁移必须同步更新配置、入口、门禁和文档关系。
- 当前 `project-memory/` 的 54 篇旧记忆迁移记录连接 50 个正式事实源，共有 107 条证据关系；继续双轨维护会产生事实漂移风险。
- 当前工作区只有用户未跟踪的 `.claude/`，本任务不得触碰。

### 合理推断

- 仅移动目录而不重新划分职责，会把现有架构、模块和项目记忆的重叠原样带入新结构，不能达到统一规范目标。
- 将历史记忆迁移记录保留在 `99-归档`，并让当前事实只存在于正式领域，可同时满足追溯和唯一事实源要求。

### 假设与开放问题

- 本任务沿用已确认的产品事实，不重新讨论产品范围与技术选型。
- 运行手册只发布已有代码、部署记录和验证支持的当前操作，不把未验证目标写成当前事实。

## 用户批准的方案

- 2026-08-13，用户明确批准：不论改动大小都执行完整迁移，必须按统一规范整理知识库，服务后续 Agent 检索和人类关系网络查看。
- 本任务继续在当前 `v2` 分支串行执行，不创建新分支。
- 迁移完成前不得把目录移动本身视为完成；必须通过关系、检索和质量门禁验收。
