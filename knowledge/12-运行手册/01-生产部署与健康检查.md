# 生产部署与健康检查

## 事实源

- 编排文件：`infrastructure/cloud/compose.yml`
- 公网入口：`infrastructure/cloud/Caddyfile`
- 环境变量示例：`infrastructure/cloud/.env.example`
- 镜像构建：[Runtime images 工作流](../../.github/workflows/runtime-images.yml)
- 已验证发布：[首个运行切片发布记录](../15-发布记录/mem-20260807-221.md)

## 仓库当前发布单元

- `edge`：Caddy（自动 HTTPS 反向代理）占用公网 80、443 和 443/UDP。
- `web`：手机 Web 静态应用。
- `api`：FastAPI（Python 接口框架）云端服务，提供就绪健康检查。
- `worker`：独立模型与耐久任务工作进程。
- `postgres`：PostgreSQL 18 主事实数据库。
- `migrate`：按需执行 ArcMind Alembic（数据库版本迁移工具）迁移。
- `queue-migrate`：兼容保留的服务名，实际只对空数据库首次初始化 Procrastinate 队列 Schema，不是可重复执行的升级迁移。
- `database-roles`：在迁移后创建或刷新两档数据库权限；API（应用程序接口）和 Worker（后台工作进程）共用受限运行账号。

## 发布顺序

1. 使用固定 Git 提交对应的镜像标签设置 `ARCMIND_IMAGE_TAG`，不得依赖浮动 `v2` 标签作为唯一回滚依据。
2. 在替换生产 `compose.yml`、`.env` 或镜像标签前，使用当前线上版本仍可工作的所有者账号备份流程生成 `pg_dump -Fc`，通过 `pg_restore --list` 结构检查，并把恢复命令和上一固定镜像标签记录到当次发布台账。首次账号密码切换不能先替换成只认 `arcmind_runtime` 的新版备份脚本，因为此时运行角色尚未创建。
3. 在部署目录准备受权限保护的新版 `.env`，新增登录密码摘要和运行数据库密码；不得把真实密钥写入仓库或知识库。
4. 拉取固定镜像，但先不要启动依赖 `arcmind_runtime` 的新版 API 和 Worker。
5. 使用所有者账号运行应用数据库迁移。仅当 `procrastinate_jobs` 等队列对象确认不存在时，才运行一次 `queue-migrate` 初始化空库；对象已存在时先核对当前与目标 Procrastinate 版本和结构，不得重复执行 `apply_schema`。供应商版本变化必须把其 `sql/migrations` 纳入独立批准的数据库迁移，不能用全量 Schema 覆盖升级。
6. 运行 `database-roles`，创建或刷新运行账号对现有表、序列和未来对象的权限。
7. 启动新版 Compose 项目，检查 API、Web、PostgreSQL 和 Worker 健康状态。
8. 立即使用新版受限运行账号执行一次备份和结构检查，确认后续定时备份没有因账号切换失效。
9. 按[第一阶段测试矩阵](../11-测试与验收/03-phase-1-test-matrix.md)验证公网账号密码、会话恢复、文字事件、退出、重启和回退判据。

任一步失败都停止后续步骤。迁移后但启动前失败时，优先修复角色或配置；只有明确选择回退时才按已验证备份和上一固定镜像执行恢复，不能假设结构降级会恢复已经删除的验证码挑战数据。

生产服务器上的实际命令、凭据和 IP 不写入本知识库。一次发布的镜像提交、验收结果和剩余风险写入[发布记录地图](../15-发布记录/00-发布记录地图.md)。
