# 知识库维护规范

## 目录契约

- `00-入口`：只放总导航和知识治理规则。
- `01-项目定义`：项目身份、愿景、范围、用户、路线和统一术语；不放实现细节。
- `02-业务模型`：业务概念、状态、不变量和跨模块流程；不放数据库字段或页面结构。
- `03-系统架构`：系统上下文、端侧职责、部署单元和依赖方向；不复制端内实现。
- `04-接口与事件`：跨端 API（应用程序接口）、事件、命令、错误和机器契约；不暴露模块内部模型。
- `05-数据模型`：实体、关系、数据所有权、事务、持久化和迁移。
- `06-前端设计`：页面、路由、交互状态、前端工程和前端模块。
- `07-后端设计`：云端服务、后端模块、业务执行、后台工作和可观测性。
- `08-安全与合规`：身份、授权、密钥、隐私、审计和威胁边界。
- `09-技术调研`：候选方案、外部证据、验证动作和排除原因；未经决策不得冒充当前事实。
- `10-架构决策`：已接受的重要取舍、替代方案和后果。
- `11-测试与验收`：完成标准、测试矩阵和可复现证据。
- `12-运行手册`：当前可执行的部署、监控、备份、恢复和排障步骤。
- `13-已知问题`：仍有效的缺陷、风险和开放问题。
- `14-开发方案`：隔离任务舱；不进入正式知识索引。
- `15-发布记录`：已经验证的实现、部署和版本结果；不替代当前架构事实。
- `20-79`：在总地图登记后的项目专属领域；不得改变公共编号含义。
- `90-模板`、`99-归档`、`_attachments`：固定保留区，不进入正式知识索引。

项目不具备某项能力时可以不创建对应目录；一旦具备，该目录和唯一内容地图就是强制要求。ArcMind 已具备前端、后端和生产运行态，因此 `06`、`07` 和 `12` 必须存在。

## 单一事实源

- 同一事实只能有一个主归属；其他文档使用有语义的 Markdown 链接引用。
- 产品事实、决策、开放问题、实现结果分别进入其职责目录，不额外复制“项目记忆摘要”。
- 代码和测试是实现行为证据；用户确认与正式知识定义业务目标；发生冲突时必须显式记录并修正过期知识。
- `99-归档` 保留历史追溯，不作为当前事实或默认 Agent 检索依据。

## 知识状态

- `draft`：结构化草案，不能直接作为稳定实现依据。
- `current`：当前有效且可以作为开发依据。
- `assumption`：为分析暂用但尚未验证。
- `stale`：可能与当前证据冲突，使用前必须复核。
- `deprecated`：已经废弃，正文应指向替代知识。

任务舱使用独立生命周期：`draft → confirmed → active → done`。纯讨论只能修改 `draft` 任务舱；用户确认完整方案和有序清单后才能实施。

默认检索会优先返回 `current`，但不会隐藏 `draft`、开放问题或废弃知识。检索结果必须显示状态；需要调查未决事项时使用显式状态过滤并回到原文复核。

## 最小知识契约

```yaml
id: 稳定且唯一的知识标识
type: 合法知识类型
status: draft/current/assumption/stale/deprecated
summary: 能表达真实结论的一句话
last_verified: YYYY-MM-DD
```

摘要必须说明结论或边界，禁止只写“某文档的当前事实、边界与关联依据”这类标题包装。

## 关系规则

- 每个正式领域必须有唯一命名的 `00-*-地图.md`。
- 总地图只连接领域地图，领域地图连接本域知识，避免单中心星状图。
- 当前有效知识必须被所属领域地图收录，并至少具有一条有语义的内部关系。
- `current` 文档引用 `draft` 时，链接文字必须显式包含“草案”“待定”“待确认”或“开放问题”等状态含义；开放问题类型本身可以作为风险指向，但不能作为稳定实现依据。
- 链接用于表达依据、细化、实现、约束、决策、验收或发布，不为增加连线数量而连接无关文档。
- 新增、移动、废弃知识时同步更新领域地图和受影响的语义关系。

## 附件和 Obsidian

- Markdown 是事实源；Canvas 和关系图只是视图。
- 个人工作区、社区插件、主题、缓存和本地索引不得提交。
- 音视频、安装包、数据库和大体积生成物默认不进入 Git；例外必须在任务舱记录用途、体积和存储方案。

## 发布检查

修改后必须运行 Agent Context OS 校验、项目结构门禁、索引重建、固定检索、断链、关系孤岛和跨状态关系检查。固定检索至少覆盖任务隔离、当前登录方式与迁移状态、生产模型和 API 变更。只在这些证据通过后，任务舱、正式知识和发布记录才能一起完成。
